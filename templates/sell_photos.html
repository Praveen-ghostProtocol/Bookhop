ONE FILE PER REQUEST. SYSTEM §4.5: *"on 3G a 4-file request that dies at 90% loses all four; four requests lose one."* With JavaScript off that property is free rather than engineered — one input, one submit, one round trip — and the page that comes back IS the resumable state. There is no queue, so there is nothing to lose and nothing that can claim to be saved while it is not (SYSTEM §1 rule 9; ADR-001 §6 excludes offline writes outright). THE LISTING ALREADY EXISTS AS A DRAFT BEFORE ANY PHOTO IS SENT, which is why this screen is survivable: the typed description, the ISBN and the price are never at risk from a photo failure. EC-13 and AC-S1.3, and the reason `create_listing` and `publish_listing` are two calls. THE FIVE STATES OF SYSTEM §4.5, AND WHERE EACH ONE IS: default — zero rows: the control, the hint, and `sell.photos.hint`. partial — some uploaded, more possible: `sell.photos.partial` counts them and **the publish button stays enabled**, because photos are not required. error — a refused file: the message is in the field's error slot with what to do next. The two reasons are different sentences because they have different next actions — a file we cannot read needs a different file; a fifth photo needs none. disabled — four photos: the control is GONE and the reason is in text beside it. SYSTEM §2.2: *"a disabled control with no stated reason is a defect"*, so there is no greyed control here at all, only the sentence. empty — publishing with none: `sell.photos.none`, stated as a fact. Not an error. LOADING AND OFFLINE ARE THE BROWSER'S, DELIBERATELY. §4.5 specifies a determinate progress bar driven by `XMLHttpRequest.upload.onprogress`; there is no JavaScript in this product, so what the student gets is their browser's own upload indicator, which is determinate, native, and costs zero bytes. A dropped connection is the browser's error page, and on return this page shows exactly what landed. **Neither is simulated and neither is claimed.** `trust.exif` IS ON THIS PAGE AND THIS IS THE SLICE IT BECAME TRUE IN. COPY-DECK §9a held it back from the S1 help page because the EXIF step did not exist; `listing_photos.exif_stripped_at` is NOT NULL, so the row cannot exist unless the strip happened — the sentence describes a structural guarantee, not an intention.
